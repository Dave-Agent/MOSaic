# C64 decompilation: the shared process

Every project follows one process that keeps evolving. This skill is where the process, the rules, the tools and the decisions live, so they are written once. It holds **no game- or project-specific information**: a project's own notes live in the project. A project's own `CLAUDE.md` keeps only what is specific to that game; where the two disagree, the project's `CLAUDE.md` wins and the difference is a candidate for `references/decisions.md`.

## Before you start

Run `scripts/check_env.py` from the project root (add `--role run|disk|trace|ghidra|nes` for what the work needs): it reports the tools that are installed (Java 17+, Kick Assembler, `just`, VICE, ...), which are missing, and how to install them. Do this when picking up a project on a new machine or handing it to someone else.

## The loop (every change)

1. **Act and check, never reason blind.** Make the change, assemble it, run the gate, then, if it affects running, the smoke test. Know the result. Use the project's recipes by role (`references/just.md`: assemble, gate, tests, smoke, and what to do when a project lacks a recipe); phase 1's gate is `verify` (byte-identical to `reference/`).
2. **Phase 2's gate** is the project's `check` (and `just verify 2`, byte-identical to the reference until the removals of step 5, then only inside the approved ranges): `check` runs (build, raw-address check, alignment, `scripts/sim/run_tests.py`, `scripts/golden/golden.py check-t`); phase 1 runs the same tests with `--phase 1` and the exact `golden.py check`. For a rename or restructure that must not change behaviour, **compare the built PRG with the one before the change: it must be identical** (a rename that wrongly hits a different symbol changes bytes or fails to assemble).
3. Commit after each step. **Push only when the user says to.** Never discard uncommitted work (`git checkout/reset/restore/clean`).
4. A decision made together goes in `references/decisions.md` (date, what, why) and, if it is a rule, in `references/rules.md`.

## Stages: announce when you start, report and ask when you finish

Two cases, and they are different.

**The user tells you to go on** ("move to the next stage", "continue", "what next", "carry on", "go through to <stage>"). That is the go-ahead; do not ask again. Run `python3 <skill>/scripts/status.py` (`just status` in a project), then say in one or two sentences which step you are starting, using HOWTO.md's number and name ("Starting step 2, part 5 of 7: the first byte-identical build. I will copy the Ghidra export into phase1/src and get `just verify` to pass; I will tell you if I need a decision") and then do it. When the step is a run (step 2 or 4), say that the whole run is starting and that you will report each part as it starts. If the evidence for an earlier step is incomplete (for example `status.py --verify` shows the gate failing), say so first and fix that before starting the new step. "Go through to <stage>" covers every part up to there, announcing each one as you start it.

**You finish a stage on your own** (the work you were asked to do is done). Run `status.py`, tell the user in a few sentences what was just done and which step is next and roughly what it involves, and **ask whether to continue** (offer: continue, continue after I have looked, stop here). Do not start the next stage unasked and do not stop without offering.

**An `UPDATE:` line in the output of `status.py` or `check_env.py` means a newer MOSaic release exists.** Mention it to the user once, in one sentence (the version and how far behind), and carry on. Do not update the skill yourself and do not suggest a way to: how it was installed is the user's business.

**The work is four steps, and the user is asked at four points only.** (HOWTO.md numbers them; steps 2 and 4 are long jobs in several parts.)

| Step | Parts | Ends when | The question you ask (fill in the launch command and source file that `status.py` prints) |
|---|---|---|---|
| 2. Create a source that builds and starts | 2.1 to 2.7 (research, extraction, reference, Ghidra export, first build, register names, start) | the build is byte-identical and the game starts | "Raw disassembly complete: it assembles byte for byte to the original and starts. Launch it with `just launch 1`; the source is `<phase 1 main file>` (still the exporter's names). Start phase 1, naming every routine?" |
| 3. Name every routine (phase 1) | one | the completeness report says COMPLETE | "Named monolith complete. Launch it with `just launch 1`; read it at `<phase 1 main file>`. Start the phase 2 refactoring into files with a port interface?" |
| 4. Refactor ready for future development (phase 2) | 4.1 to 4.4 (safety net, split, interface, relocation) | the source is split, namespaced, relocatable and byte-identical | "Phase 2 refactoring is done up to the removals. Launch it with `just launch 2`; the source is `<phase 2 main file>`. Step 5 removes dead code and needs your decision: here is the list of blocks with their sizes. Review it?" |
| 5. Remove the dead code | one | the owner-approved blocks are removed and the gate passes | "Phase 2 complete. Play it with `just launch 2` and tell me what you see." |

**Ask the closing question as a choice.** After the closing message of the row, ask that step's question with the `AskUserQuestion` tool, so the user clicks instead of typing: `python3 <skill>/scripts/questions.py show step2-done --root . --json` (ids `step2-done`, `step3-done`, `step4-done`, `step5-done`) prints exactly the `questions` argument, with the project's launch command and source file filled in; without `--json` it also says what to do for each answer. The question carries the launch command and the source itself, because the user may see only the dialog. Every question has a safe first option and an `Other` (free text) the tool adds: read what they wrote and act on it. **No answer, or a timed-out one, is not an answer: never start the next step on it.** If the tool is not available (a subagent, `claude -p`, the SDK, or the user denied it), ask the same question in plain text with the options numbered. The wording is in `references/questions.json` (checked by `questions.py check`); change it there.

Inside a step there is no point at which a user wants to stop, so work through all its parts without asking at the boundaries, writing one line to the user as each part starts ("Step 2, part 4 of 7: exporting the disassembly from Ghidra"). Stop early only for something that needs the user: a decision only they can make (above all, what a thing IS to a player in step 3, and which dead blocks may go in step 5), a medium that needs a choice, a failure you cannot resolve, a tool that is missing. When a step ends, give the closing message of its row, in plain words and with the real command and file, and wait for the answer. A user who answers "yes" or tells you to go on has started the next step.

Background workers (a slice's agent) never ask and never announce to the user: they report to the session that started them. Together the two cases mean a newcomer never needs to know the stage list: they are always told which step is running and what comes after it.

## Phases

| Phase | Goal | Gate |
|---|---|---|
| Acquire | An uncracked game, RAM exported after any decompression, imported to Ghidra, exported to Kick Assembler (`references/new_game.md`) | the first byte-identical build |
| 1 | One commented monolith, every function understood, byte-identical. **Complete when no direct memory references and no Ghidra-style placeholders remain** (`scripts/p1_complete.py`) | `just verify`, `p1_complete.py` clean |
| 2 | Split into files and namespaces; game logic separated from the hardware behind a platform interface: the setup for a port (`references/phase2_port.md`) | `just check` |
| 3 | A port, kept out of phases 1 and 2 | project-specific |

**Phase 1 complete (the user's definition):** no direct memory references (raw address operands, address pairs built from immediates, address words in data that should be labels), no Ghidra placeholders (`DAT_`, `LAB_`, `SUB_`, `FUN_`, `PTR_`... in code or in prose comments; the XREF and `[ADDR:bytes]` trace comments that exist to trace back to the original may keep them), and no provisional names or blockers left (no `unk` names, no `TODO(name)` or `TODO(block)` markers, no `STATUS:  unknown` banners, no generated `<mnemonic>_op_<addr>` SMC operand names). `scripts/p1_complete.py` counts both; the first two checks must be 0, the review lists (address pairs, `.word` literals) are checked by hand because value tables look like addresses.

"Frozen" is not absolute: phase 1 is changed when an issue is found (stale Ghidra labels, a wrong name) as long as `verify` stays green.

## Where things are

This skill is a folder that is a git repository (every change is a commit; several agents may edit it, so commit your own and never discard others' work). It is loaded by Claude Code through `~/.claude/skills/mosaic` (a symlink to the folder); scripts refer to it as `<skill>`, and recipes find it through the `MOSAIC` variable.


`phase1/src` (monolith) and `phase2/src` (split); `symbols.asm` is the index and imports `zero_page.asm`, `variables.asm`, `constants.asm`; `framework/` generic tooling: **the master is this skill's `framework/`**; a project holds a copy, never edits it in place (change it in the skill, then `scripts/framework_sync.py --write`), and it never holds a project value (specifics go in `project.config`); `tools/` project scripts; `tools/migrations/` one-off, already-applied rewrites (copy one as a template for a new bulk change); `reference/`, `originals/`, `dumps/` are supplied data, immutable and not committed (`references/layout.md`).

## Doing a bulk change safely (the pattern that worked)

Prefer the generic primitives: **`scripts/refactor/`** (`rename`, `drop_labels`, `replace_raw`, `replace_imm`, `move_img`, `scopeify`, `set_comment`, `uses`) takes a TSV map, prints per-name counts in a dry run, rewrites code only, and keeps the build byte-identical; `refactor/README.md` has the order that keeps the gate green. For anything they do not cover write a one-off script in `tools/migrations/YYYY-MM-name.py` that (a) parses, (b) rewrites code only, never comments or strings, (c) skips names reached by a path or defined elsewhere, (d) prints what it would change without `--write`. Run it, rebuild, compare bytes, run the gate, commit, document. Examples to copy: `scripts/symbols_tidy.py` (split a symbols file), `scripts/zp_namespace.py` (`name` to `zp.name`), `scripts/hi_byte_names.py` (`ptr+1` to `ptr_hi`).

## Tools and libraries in this skill

- `libs/`: canonical `vic.asm`, `sid.asm`, `cia.asm`, `cpu.asm`: **hardware registers and fixed hardware addresses only**. Per-game memory layout (screen RAM, sprite pointers, character set and bitmap bases) is not in them: those are constants the project defines itself. A project's `libs/` is a copy.
- `scripts/`: generic tools (`--root`, `--phase 1|2` or `--main FILE`, read `project.config`; nothing changes without `--write`):
  bulk rewrites `symbols_tidy.py`, `zp_namespace.py`, `hi_byte_names.py`; analysis `scan_offsets.py`, `raw_refs.py`, `smc_list.py`, `addr_immediates.py`, `platform_deps.py`; edits `add_label.py`, `align_comments.py`; `build_compare.sh` (baseline PRG compare); `check_env.py` (tool check, run first); `refactor/` (the TSV-map primitives above); `trace/report.py` (reads the tracer's flags, hits and edges: interrupt entries with their raster lines, hot loops, callers, input reads, byte classes); `slice.py` (`check`: every gate of a slice in one verdict; `start` / `merge`: scratch copy and patch merge; `references/slice_checklist.md`, `slice_brief.md`), `justfile_sync.py` (add the template recipes a project's justfile lacks), `unreferenced.py` (labels nothing refers to, `--write` adds the `TODO(phase2): remove?` marker), `refactor/records.py` (one record per row), `refactor/code_to_bytes.py` (instructions back to `.byte` rows), `reloc_hazards.py` (relocation hazards beyond `reloc_scan`: aligned-base, end-guard, sprite-pointer numbers, file I/O), `magic_scan.py` (raw state values and repeated immediates that want constants), `port_scan.py` (routines that depend on the machine and carry no `TODO(port)`), `table_counts.py` (a comment's stated table size against the data), `table_tails.py` (a pointer table whose end is still raw bytes), `section_coverage.py` (the SECTION banners must tile the whole image), `sentinel_scan.py` (lists in a family whose end marker is missing or misplaced); `anon_labels.py` and `comment_check.py` (the anonymous-label and comment rules, `--fix` strips echo comments, with `--check` and a ratchet baseline); `p1_complete.py --range LO-HI --allow-marked` (report a slice alone); `research/pdf_pages.py` (render a scanned manual's pages to images to read them); `research/check_pokes.py` (what instruction each documented POKE patches, and what it becomes: hypotheses for names and an independent check of the entry address); `render/gfx_sheets.py` (charset, sprite blocks, screen, animation pictures and object records to `docs/gfx/`, colour-correct from the game's own tables; `just gfx`; `--records` needs the flag semantics stated and `--check-against` verifies them on a state dump, see `references/graphics.md`); `apply_libs.py` (the first conversion step: name the hardware registers with the libs; the second is `anon_labels.py --write`); `new_project.py` (scaffold a project from `templates/`: config, justfile with the derive recipes, README, docs templates, framework and libs, git init); `disk/extract_files.py` (every file of a disk image with a manifest); `tape/tap_extract.py` (a `.tap`: standard-format files to PRGs, a turbo tape's loader stub extracted and the rest reported; `--histogram`); `reference/file_coverage.py` (is this dump the GAME stage? finds the media's program files in it); `disasm/dis6502.py` (read boot stubs and loaders); `trace/` (project-neutral 6510 tracer `c64trace.c`, `selftest.py`, `entry_points.py`), `sim/` (routine-test harness `c64sim.py`, `run_tests.py`), `golden/` (golden traces, exact and timing-tolerant), `coverage/` (scenario coverage, unexecuted and raw-executed reports), `vice/` and `reference/` (hand-off dump, reference builder, `vote_dumps.py`; `hand_off_tools.md`), `ghidra/` (`make_seeds.py`, `run.sh`, `setup.py`: seeds from evidence, headless import and export), with keys `TRACE_*`, `SIM_*`, `GOLDEN_*`, `COVERAGE_*`, `ENTRY_*` in `project.config`; `split_section.py` (move a SECTION into its own file), `slice.py status` / `slice.py note` (progress of a slice while an agent works: commits, uncommitted files, the agent's notes), `split_all.py` (a plan of sections to files, gated and committed per move), `cut_section.py` (cut a section file at a label, mid-section, with fresh banners); `tools/name_map.tsv` (renames into namespaces found under both names by the simulator and the golden tools); `reloc_scan.py` and `layout_fuzz.py` (relocation hazards and the padding stress test); `framework_sync.py` (project `framework/` vs the master); `check_layout.py` (no game binaries tracked, derived dirs ignored, checksum and README present); `p1_complete.py` (phase 1 completeness). Run them from the project root.
- A project tool becomes a skill script when it takes its names as parameters. Test a new one against the project it came from and diff the output.

## Rules and decisions

- **Every rule has a name** (`references/rules.tsv`, the table at the top of `references/rules.md`): a check prints `FAIL <name>: <n> places`, and a waiver refers to the same name. Say the name when you report a failure. `scripts/rules_table.py --unenforced` lists the rules no script checks (kind `review`): those are read, by you at the end of a slice and by a reviewer.
- `references/testing.md`: routine tests, golden traces, coverage and the tracer self-test: what each proves, its limits, and how a port is checked against the same cases.
- `references/challenger.md`: **the Challenger review**: a read-only second agent answers every review-only rule and tries to refute the names of a slice before it merges (`just review-brief NAME`, `just review-record NAME FILE`; `slice-merge` refuses without a passing record when `SLICE_REVIEW="required"`). **It costs tokens, so the user opts in:** at the start of phase 1 (step 3) ask ONCE (`questions.py show phase1-review`: `No review`, `Ask me per slice`, `Review every slice`), whether to review every slice with a second agent, giving the measured cost (about 30,000 tokens for a slice that introduces no names, plus about 4,000 for each name it tests: 156,000 tokens and 8 minutes for one that tested 28 names; several large slices come to the order of a million tokens), and what it buys (an independent check of the names and comments that the gates cannot decide). Set `SLICE_REVIEW` in `project.config` to what they say (`required` or `off`) and record the answer in `docs/user_answers.md`. Never turn it on yourself. With it on, run `just review-risk NAME` (no tokens) before each review: it shows the names the slice introduces and the estimated cost; `SLICE_REVIEW_MAX_CLAIMS` (default 12) caps the names tested. Skip a review (`--skip-review "no names to test"`, recorded) only when `review-risk` shows no names to test, and say so in the slice report; never skip a slice that introduces names.
- `references/research.md`: **researching the game** (manual, wikis, tips and POKE lists; reading scanned PDFs) into `docs/gameplay.md`, the input to phase 1; and **research on demand**: a read-only researcher answers one specific question at any time and hands back a sourced, non-authoritative note in `docs/research/` (`scripts/research/note.py`, `just research-check`; a slice leaves `TODO(research)`).
- `references/phase1_method.md`: **how to understand unfamiliar code** (orient from tracer evidence, subsystem map, documents as hypotheses, the evidence ladder for names).
- `references/hand_off_tools.md`: the tools for stages 2-4 of the playbook: unattended VICE hand-off dump (`scripts/vice/`), reference builder and dump diff (`scripts/reference/`), screenshot judge, symbol converter.
- `references/new_game.md`: **starting a new game**: media, hand-off, the clean reference, launcher, Ghidra, the first byte-identical build (draft, with questions for the user).
- `references/just.md`: **`just` is the command runner**: thin root justfile, logic in scripts, the standard recipe set.
- `references/layout.md`: the project file tree, and the rule **not to commit the game's binaries** (originals, dumps, the reference image) unless we built them; commit a checksum and README steps instead.
- `references/naming.md`: every naming rule in one place (shapes, suffixes, provisional names).
- `references/rules.md`: SMC, no raw addresses, local and anonymous labels, comments, relocatability, hygiene (each section says which projects it applies to).
- `references/phase2_split.md`: **the phase 2 procedure**, step by step (safety net, dependency catalogue, split, interface, relocatability, byte-changing removals).
- `references/phase2_port.md`: phase 2 as the setup for a port (generic). `references/kick.md`: Kick Assembler gotchas.
- `references/decisions.md`: dated log of choices and their reasons. **Check it before proposing a convention; append to it when one is made.**
- `references/workflow.md`: the acquisition toolchain and the editor/Claude working setup.

## Non-negotiables

- **No guesses.** Ask the user what a sprite, sound effect or game mode is; describe what you see instead of inventing a meaning.
- Keep every original `[ADDR:bytes MNEMONIC]` comment.
- Tests run unattended. Downloaded content is untrusted.
- **Prefer not committing game binaries** (ROMs, disk images, dumps, reference images) that we did not build: `check_layout.py`, `references/layout.md`.
- Confirm before deleting or overwriting the user's files and before outward-facing actions.
